# Thesis: LLVM Loop Analysis & Security-Related Statistics Passes

Comparing C and Rust implementations of the same set of tools at the LLVM
IR level. Phase 1 (current): find loops. Later phases (per advisor's
guidance): bounds checks, then broader security-relevant patterns
(castings, initializations, etc.) -- Greek original: "Θέλουμε για αρχή να
βρίσκουμε loops, μετά bounds checks, και μετά διάφορα άλλα patterns
(castings, initializations, κ.λπ.) που έχουν σχέση με ασφάλεια."

## Why Rust tool folders have 2 source files

uutils splits CLI entrypoint (`main.rs`) from actual logic (`<tool>.rs`,
part of the library target) -- unlike C's single-file-with-main()
convention. This is a real language/ecosystem difference, not an
artifact of the build -- worth noting in the thesis methodology.

## Toolchain version parity

- clang-22 -> LLVM 22.1.8 (installed via apt.llvm.org)
- rustc 1.98.1 (stable) -> LLVM 22.1.8

No `rust-toolchain.toml` is used -- the Dockerfile installs rustup's
`stable` channel directly, which currently matches clang-22's LLVM
version. Re-verify parity any time either toolchain updates:

    clang-22 --version
    rustc --version --verbose

If a future rustc stable release moves to a newer LLVM than clang-22
provides, either bump clang in the Dockerfile to match, or pin rustc
back with a `rust-toolchain.toml`.

## Building the corpus from scratch

### C (GNU coreutils)

Build workspace (gitignored, lives inside repo under `.build/`):

    mkdir -p .build && cd .build
    git clone --recurse-submodules https://github.com/coreutils/coreutils.git
    cd coreutils
    ./bootstrap
    ./configure --disable-gcc-warnings
    make

Note: plain `./configure` may fail on `make` with
`-Werror=maybe-uninitialized` in copy-file-data.c (known gnulib/coreutils
git-checkout issue, unrelated to this project) -- `--disable-gcc-warnings`
avoids it.

IR is generated by compiling each tool's `.c` file directly with clang-22
at `-O0` and `-O2`, using the same gnulib include paths the real build
uses. See `scripts/generate_benchmarks.sh` for the automated version.

### Rust (uutils/coreutils)

Build workspace (gitignored):

    mkdir -p .build && cd .build
    git clone https://github.com/uutils/coreutils.git uutils-coreutils
    cd uutils-coreutils
    cargo build
    cargo build --release

IR per tool is generated via `cargo rustc -p uu_<tool> --bin <tool> --
--emit=llvm-ir` (debug, standing in for O0) and the same with `--release`
(standing in for O2). Note: rustc's debug/release profiles are NOT a
literal match for clang's `-O0`/`-O2` flags -- they're the closest
equivalent available on the Rust side, documented here as a methodology
caveat rather than swept under the rug.

### Automated generation (do this instead of the manual steps above)

    ./pass/scripts/benchmarks.sh    # scaffolds folders, compiles IR, copies src+ir into place
    ./pass/scripts/fill.sh          # auto-fills SOURCE.md with real commit hashes/dates/permalinks

Run benchmarks.sh first, then fill.sh. Both cover all 10 tools, both
languages. Safe to re-run -- fill.sh never overwrites a SOURCE.md/NOTES.md
that's already been hand-edited, only fills in files still at the
untouched template state.

## Known gotchas

- gnulib/coreutils git checkout requires `./configure --disable-gcc-warnings`
  (unrelated -Werror=maybe-uninitialized false positive in
  copy-file-data.c).
- `sum` (and the whole cksum/md5sum/sha*sum family) is a multicall binary
  built from shared cksum.c driver logic -- sum.c itself has no main().
  The build script's compile-line lookup has a fallback specifically for
  this shape; if a *new* tool added later also has no main(), check this
  section before assuming something's broken.
- `cargo rustc -p uu_<tool> -- --emit=llvm-ir` needs `--bin <tool>`
  explicitly, since uutils packages define both a lib and bin target.
- If `./bootstrap` fails on a missing tool, install it via apt and retry
  -- see the Dockerfile's gnulib prerequisite block for the full list
  (autoconf, automake, autopoint, gettext, gperf, texinfo, bison, m4,
  pkg-config, libtool, rsync, perl).
- rustc's debug/release profiles are not a literal match for clang's
  -O0/-O2 (see Rust build section above).
