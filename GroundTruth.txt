duffs_device
  loops: 0
  status: CONFIRMED 0 LOOPS (previously the VERIFY case)
  why: the switch statement jumps directly into sw.bb2..sw.bb20, blocks
  that sit between do.body and do.cond -- meaning do.body does NOT
  dominate do.cond on every path (you can enter mid-loop-body, skipping
  the presumed header entirely). LLVM's LoopInfo is strictly
  dominance-based, so the do.cond -> do.body back edge doesn't qualify
  as a natural loop despite the do-while syntax and the visible cycle in
  the CFG. Actual pass output: zero loop lines for this function, only
  the FUNCTION marker. This is a real, citable limitation of
  dominance-based loop detection on CFGs with multiple entry points into
  what a human would call "the loop body."

CAVEAT CARRIED FORWARD INTO STAGE 6
=====================================
Rust debug-build IR pulls in a large number of std/core/alloc functions
that have nothing to do with the tool's own logic (drop glue, RawVec
internals, iterator adapter plumbing, etc.) -- confirmed directly in the
loops.rs run, where roughly 40 std-library functions appeared alongside
the ~9 functions actually written in loops.rs, with only one of those
~40 (a monomorphized Range::fold instantiation) containing an actual
loop. This ratio is expected to be similar or worse across the real
20-tool corpus. Comparing raw loop counts between C and Rust IR without
accounting for this will conflate "the tool's own algorithm" with "how
much of the standard library got inlined into this particular crate's
debug build" -- a filtering step (by function name, likely via the
demangled name already added to the pass output) is needed before any
cross-language loop-count comparison is methodologically sound. Not yet
implemented -- decide and implement before drawing any conclusions from
Stage 6 output.
